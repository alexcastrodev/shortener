# Languages (i18n)

The frontend ships `en` (the default) and `pt-PT`. Text lives in `frontend/app/i18n/{language}/{namespace}.json`, one file per namespace and language, so parallel PRs rarely touch the same file.

## Writing text

- Every new string in the interface is added to `en` **and** every other language, by key, in the namespace of its feature (`auth`, `dashboard`, `links`, ...). Text written by an account owner (questions, titles) is not translated. Emails are rendered by Rails and are not covered by this guide until they are localized (I12).
- Keys are flat and in `snake_case`. Placeholders are `{{name}}`. Plurals use i18next suffixes (`_one`, `_other`).
- In components: `const { t } = useTranslation('auth')`. Outside components, only in code that runs in the browser (event handlers, mutations): `i18n.t('auth:key')`, or `i18n.getFixedT(null, 'auth')` for a typed `t`. The server renders every request with an instance of its own, so anything that runs while a page renders goes through `useTranslation`, or receives `t` from a component that does. A `meta` function builds its `t` with `i18nFor(matches[0]?.loaderData)` (see `routes/f/preview.tsx`). Never call `i18n.t` at module scope: the strings are not loaded yet when a module is imported.
- Keys are typed from the `en` files (`app/i18n/i18next.d.ts`), so a misspelled key or namespace fails `npm run typecheck`.
- Dates and numbers go through `app/i18n/format.ts` (`formatDate`, `formatDateTime`, `formatNumber`, `formatCurrency`), never through a fixed locale such as `en-US`. A component with no `t()` of its own calls `useLocale()` so it re-renders when the language changes.

## How the strings reach the page

No language is bundled with the app. Each namespace of each language is a chunk of its own, and a page receives only the namespaces of its route:

- `app/i18n/namespaces.ts` declares, per route pattern (`/f/:publicId`, `/app/forms/:id`), the namespaces the route and everything it imports use.
- On a document request the root `loader` (`app/root.tsx`) picks the language (cookie `kurz_locale`, then `Accept-Language`, else `en`), reads the route's namespaces in that language and returns them. React Router serializes them into the page with the CSP nonce, the server renders with an i18next instance created for that request, and the browser starts in the same language with the same strings, without another request. Document responses carry `Vary: Cookie, Accept-Language`.
- On client navigation the root `clientMiddleware` loads the namespaces of the next route, in the current language, before it renders. If a chunk cannot be loaded (a tab opened before a deploy asks for a file the new release no longer has), the browser opens the next page as a new document, which brings the strings with it.
- The prerendered pages (`/`, `/login`, `/login-confirmation`, `/about`, `/report`) are built without a request, so they are in `en`. After hydration `useLocaleSync` switches to the cookie, the account's saved language or the browser's, and so does the switcher in `/app/account`: the namespaces already on the page are loaded in the new language first, and the language changes only once they are there. If they cannot be loaded, the page stays in the language it shows.

## The check

`npm test` (also run by the `frontend` job in CI) fails when, for any language other than `en`:

- a namespace file is missing;
- a key exists in one language and not the other (plural suffixes are ignored);
- a `{{placeholder}}` differs;
- an `en` key is not referenced anywhere in the source (as `'key'` or `'ns:key'`).

A namespace whose translated file is `{}` is skipped until it is translated. Nothing falls back to `en` at runtime, so such a file shows its keys: keep it out of a released language.

It also follows the imports of every route in `app/routes.ts` and fails when a route uses a namespace it does not declare in `app/i18n/namespaces.ts`, or declares one it does not use. The failure prints the list to write.

## Adding a language

1. Add the tag to `LOCALES` in `app/i18n/locales.ts` and teach `match()` which browser tags map to it.
2. Create `app/i18n/{tag}/` with one JSON file per namespace in `app/i18n/en/`. The files are found by `import.meta.glob`, so nothing is imported by hand. There is no fallback to `en` at runtime, so fill every file before the language is added to `LOCALES`.
3. Teach `activeLocale()` in `app/i18n/index.ts` the new tag, for dates and numbers.
4. Run `npm test` and `npm run typecheck`. The check picks the new language up from `LOCALES`.
5. Look at the screens in the browser: translations are often longer than English and can clip in narrow buttons.

## Adding a namespace

1. Create `app/i18n/{language}/{namespace}.json` in every language.
2. Add its type to `resources` in `app/i18n/i18next.d.ts`.
3. Use it, then run `npm test`: it names the routes whose declaration in `app/i18n/namespaces.ts` must list it.

Legal text (`/privacy`, terms) is only published in a new language after a human review.
